# Schema baseline — methodology and scope

## Why this exists

Creating an isolated Supabase test branch (`frontend-backend-reconciliation-test`,
see [PRODUCTION_TEST_INCIDENT.md](PRODUCTION_TEST_INCIDENT.md)) failed on the very
first migration: `20260628234515_v9_document_intelligence.sql` does
`ALTER TABLE documents ADD COLUMN ...`, but `documents` doesn't exist — no
tracked migration file creates it.

Comparing production's live schema against every `CREATE TABLE` statement in
`supabase/migrations/*.sql` found **40 tables** (of 91 total) that exist in
production but were never created by any tracked migration — they predate
migration tracking or were created out-of-band (e.g. directly in Studio).
Same pattern for 6 functions and 15 triggers. This baseline captures exactly
that gap, so replaying the repo's migrations from an empty database
reproduces production's actual schema.

## Methodology

Everything below was generated by direct, read-only introspection against
production (`pg_catalog` / `information_schema` — the same data `pg_dump`
itself reads), never reconstructed from memory:

- Column definitions: `pg_attribute` + `format_type()` + `pg_get_expr()` for
  defaults + `attidentity` for identity columns.
- Constraints (PK/FK/UNIQUE/CHECK): `pg_constraint` + `pg_get_constraintdef()`.
- Indexes: `pg_indexes` (excluding ones already backing a PK/UNIQUE constraint).
- Functions: `pg_proc` + `pg_get_functiondef()` — full, faithful function bodies.
- Triggers: `pg_trigger` + `pg_get_triggerdef()`.
- Event triggers: `pg_event_trigger`.
- RLS policies: `pg_policies` (used to confirm scope, not to duplicate DDL — see below).
- Extensions: `pg_extension`.

## What's in the baseline vs. what's already tracked

**Phantom (in `20260627000000_schema_baseline.sql` /
`20260812000000_baseline_foreign_keys_functions_and_triggers.sql`):**
- 40 tables: `tenants`, `companies`, `roles`, `company_users`, `projects`,
  `documents`, `pages`, `sheets`, `sheet_corrections`, `chunks`,
  `document_intelligence`, `document_processing_events`, `memories`,
  `conversations`, `messages`, `takeoff_items`, `estimate_items`,
  `change_order_items`, `rfi_items`, `submittal_items`, `punch_list_items`,
  `permit_items`, `procurement_items`, `daily_logs`, `schedule_tasks`,
  `contacts`, `project_notes`, `project_events`, `project_risk_digests`,
  `civil_construction_entrances`, `civil_material_ledger`, `civil_pipe_runs`,
  `civil_stockpiles`, `civil_surfaces`, `earthwork_volumes`, `audit_logs`,
  `ai_agent_audit_trails`, `google_connections`, `generated_documents`,
  `cost_catalog`.
- 6 functions: `_set_updated_at`, `set_updated_at`, `claim_document_checksum`,
  `match_chunks` (2 overloads), `rls_auto_enable` (a `SECURITY DEFINER` event-
  trigger function that auto-enables RLS on any new `public` table — a real
  safety net, preserved as-is).
- The `ensure_rls` event trigger wiring `rls_auto_enable` to `ddl_command_end`.
- 15 `updated_at` triggers on the phantom tables.
- ~85 indexes (including the `chunks` HNSW vector index and `takeoff_items`'
  PostGIS GiST indexes).
- 5 extensions: `uuid-ossp`, `pgcrypto`, `vector`, `postgis`, `postgis_topology`.

**Deliberately NOT duplicated — already correctly tracked:**
- RLS enablement + policies for all 40 tables. Verified by grep: policy names
  matching every phantom table (`tenant_isolation_*`, `*_service_role_only`,
  etc.) already exist in `20260706_rls_tenant_isolation.sql`,
  `20260706_rls_profiles_and_catalog.sql`, `20260714_backfill_rls_policies.sql`,
  and several later per-feature migrations. These migrations reference the
  phantom tables by name and will apply correctly once the baseline creates
  them — duplicating the policy DDL here would just create redundant/
  conflicting definitions.
- `pg_cron` / `pg_net` extensions — already tracked in
  `20260707_schedule_commodity_sync.sql`.
- The `purchase_orders_po_number_seq` sequence — implicitly created by the
  tracked `procurement_marketplace` migration's `serial` column.

## File placement and why it's split in two

- **`20260627000000_schema_baseline.sql`** — sorts *before*
  `20260628234515_v9_document_intelligence.sql` (the earliest existing
  migration), so the 40 tables exist before anything tries to `ALTER` them.
  Contains only columns + PK/UNIQUE/CHECK constraints — no FKs, since some
  target tables that don't exist yet at this point (e.g. `document_pages`,
  `estimate_versions`, `manual_takeoffs` are created by later migrations).
- **`20260812000000_baseline_foreign_keys_functions_and_triggers.sql`** —
  sorts *after* every existing migration. Adds all FK constraints (both
  phantom→phantom and phantom→later-tracked-table), the 6 phantom functions,
  the `ensure_rls` event trigger, the 15 phantom triggers, and all indexes —
  everything that's safe to defer until every table it might reference exists.

## A note on "tracked" migration filenames vs. production's applied ledger

The local filenames in `supabase/migrations/` do **not** reliably correspond
to the version numbers recorded in production's
`supabase_migrations.schema_migrations` table — several migrations recorded
as applied on production (e.g. `20260629232143_project_risk_digests`) have no
matching local file at all, under any name. This baseline's scope was
therefore defined pragmatically: it captures the gap between "replay every
currently-committed local `.sql` file top to bottom" and "production's actual
live schema" — which is the only definition that's actually testable and
actionable, regardless of the ledger's bookkeeping history. See
[MIGRATION_REPLAY_RESULTS.md](MIGRATION_REPLAY_RESULTS.md) for the branch-only
validation this baseline was tested against, and the separate, still-pending
decision on production's migration-ledger repair itself.
