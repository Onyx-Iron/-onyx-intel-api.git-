# Remaining Risks

1. **No scheduled outbox re-driver.** `estimate_sync_outbox` rows left `pending`/`failed` after a sync failure are only retried by a subsequent save of the same object (which refreshes the pending row). A stuck row with no further activity on that object stays unsynced indefinitely with no alert. Needs a cron/worker sweep in a follow-up.

2. **Soft-deleting a manual takeoff does not reconcile an already-synced `estimate_items` row.** The mirror (`takeoff_items`) is hard-deleted atomically with the source, but any `estimate_items` row that was already created from it is left exactly as-is — neither mutated (correct, per "approved estimate immutability") nor flagged as orphaned-source (a gap). Carried over unchanged from the prior milestone; still not fixed here, since building real reconciliation logic (what should happen to a priced line item whose source measurement no longer exists?) is an estimating-workflow decision, not a persistence-hardening one.

3. **Recalibration does not implement Step 5's full "recalculate affected drafts with financial-impact preview" workflow.** Recalibrating a sheet only changes the scale used for measurements drawn *from that point forward* — it does not offer to batch-recompute existing draft objects, show a before/after financial delta, or let the user cancel a batch recalculation. This is a deliberate scope cut (a full preview-and-apply workflow is a UI feature, not a data-integrity fix) — flagged here so it isn't mistaken for an oversight.

4. **Legacy calibrations remain render-scale-dependent until a user recalibrates.** This is the explicit, documented policy (never silently reinterpreted), but it means any sheet a user hasn't yet recalibrated is still exposed to the original bug this milestone targets. There's no forced-recalibration prompt — only a passive badge.

5. **The created-vs-updated history label has a narrow benign race.** Two concurrent first-time saves of a brand-new `client_key` could both see "no existing row" in their pre-upsert `SELECT` and both log `created` in history, even though only one insert actually wins the `client_key` uniqueness race and the other becomes an update. The underlying data is never duplicated or corrupted — only the history *action label* could be inaccurate in this rare race. Not fixed (would require `SELECT ... FOR UPDATE` or the `xmax = 0` trick, adding complexity for a cosmetic-only edge case).

6. **`calculation_formula_version` versioning has no migration story yet.** If `FORMULA_VERSION` in `quantity.ts` is ever bumped (a formula correction), there's no batch job to recompute previously-saved quantities computed under an older version — they'd simply carry the old version tag forever unless individually re-saved. Acceptable for now since `v1` is the only version that has ever existed, but worth planning before the first formula change ships.
